# Introduction

In January 2026, Moonshot AI introduced Kimi 2.5 with "agent swarms", orchestrated by agents themselves. This self-orchestrating behavior was trained via reinforcement learning ("parallel-agent reinforcement learning", PARL). With PARL, Kimi 2.5 achieved state-of-the-art scores on SWE-bench Verified (76.8%) and 3--4.5x speedups on coding tasks, with a trainable orchestrator that dynamically spawns up to 100 sub-agents across 1500 tool calls. Separately, Cursor used agent swarms to write a partially functional web browser in Rust---over one million lines of code. The swarm followed an intricate human-designed orchestration structure with planners, workers, and judges, arrived at after two failed topologies.

These results establish that orchestration structure---which agents to spawn, what context to give them, how to aggregate their outputs---dramatically affects outcomes. The same models and agents, differently orchestrated, produced qualitatively different results in Cursor's demonstration. Moreover, the early successes of PARL suggest that LLMs can learn to self-orchestrate and outperform fixed strategies. 

Self-orchestration is also a proven strategy to address the limitations of finite context. When a task would exceed the LLM's context window, a remedy is to split context across subagents. Coding agents like Claude Code deploy "Explore" subagents which can gather bits of information from a large codebase, preserving the context window of the main thread; a conceptually similar approach is taken by the Recursive Language Model (RLM; Zhang and Khattab, 2024). Whether implemented as a simple for-loop (as in OpenCode), a declarative graph over a Pregel engine (LangGraph), or a multi-agent framework (CrewAI, AutoGen), the LLM's role is the same: it receives message history, produces one response, and external code decides what happens next. The LLM never sees the execution topology, never plans multiple steps of its own control flow, and never specifies how to decompose a task into subtasks. It is a passive, one-step-at-a-time participant in a developer-authored harness. Even PARL, where the orchestration policy is learned, encodes it in model weights---opaque, monolithic, and not directly inspectable or composable.

We present Spell (Self-Prompting Execution Language for LLMs), a domain-specific language that breaks this invariant. In Spell, the LLM writes programs that control its own recursive execution. The user prompts the LLM once; the LLM's output is a program in a Lisp dialect that can call itself recursively via the `llm` primitive, manipulate what context its children see via hooks, and reproduce parts of its own source code via quining primitives. The harness simply evaluates whatever the LLM writes. Rather than the developer specifying the execution topology and the LLM filling in content, the LLM specifies the topology itself---choosing what recursive calls to make, what context to pass, and how to branch---using the same natural language medium it already operates in.

This design exploits a structural property of Lisp that has no analogue in conventional programming languages: homoiconicity, the identity of code and data. In Lisp, programs are S-expressions, and S-expressions are data that can be quoted, manipulated, and evaluated. Spell extends this principle to LLM outputs: completions are programs, and programs are data that can be passed as context to child LLMs. Natural language is itself "homoiconic" for LLMs---instructions about text are text---and Spell formalizes this by embedding natural-language chains of thought as string literals within executable S-expressions.

Three mechanisms make self-orchestration practical. First, `spell-eval`, a sandboxed evaluator with environment threading, ensures the LLM has perfect knowledge of how its code will execute: the environment of a program is the program itself. Second, `expand` automatically closes thunks over the current environment before passing them to child LLMs, so the parent need only reason about its own scope. Third, hooks---code-to-code transformers applied to completions before evaluation---enable meta-level control: injecting undisclosed context, intercepting return values, and propagating behavior recursively through the agent hierarchy. Together, these mechanisms let the LLM write orchestration logic that is inspectable (it is source code), composable (it is function composition), and formally grounded (it inherits Lisp's semantics for scope, evaluation order, and environment threading).

Spell occupies a gap in the current landscape. PARL demonstrates that model-designed orchestration outperforms fixed topologies, but represents the policy in weights---learned, opaque, and monolithic. Cursor demonstrates that orchestration topology is a first-class engineering concern, but relies on human design and iteration over harness code. Recursive Language Models (RLM) let the LLM write Python code to call itself, but mediate orchestration through a general-purpose language rather than a minimal, formally specified one. Smith's 3-Lisp (1982) introduced reflective lambdas that execute one meta-level above their caller---the closest historical precedent---but operated on symbolic representations, not natural language, and without LLMs as processors. Spell proposes a third path: orchestration as inspectable, composable source code written by the model itself, in a language designed for this purpose.

Our contributions are:

1. **A language for LLM self-orchestration.** We define Spell, a Lisp dialect with primitives for recursive self-invocation (`llm`), self-reference (`uneval`), environment-closing expansion (`expand`), tool-use continuations (`call-now`), and meta-level hooks. We provide formal semantics grounded in the Lisp tradition of meta-circular evaluation.

2. **An implementation and evaluation.** We implement Spell as a Clojure interpreter with a sandboxed evaluator, automatic expansion, a hook system, and an agent factory (`make-llm`) for configuring agent hierarchies with controlled tool access and model selection.

3. **An action space for learned orchestration.** We argue that Spell provides a constrained, formal action space suitable for reinforcement learning over orchestration policies---combining PARL's demonstrated ability to learn orchestration with the transparency and composability of source code.
