# Spell v0.2.0 Documentation Release Plan

**Status:** aligned planning checklist  
**Release intent:** first public-facing software release of Spell.  
**Scope of this plan:** documentation and public repository presentation only. API design, Python adapter design, and API documentation are intentionally excluded because they are being handled on a separate branch.

## Positioning

Spell v0.2.0 should present Spell as an experimental CLI-first implementation of self-programmed execution. The public story is:

- Spell is a language/runtime in which the model writes the orchestration program.
- A paid or authenticated LLM provider is an acceptable requirement for normal use.
- The no-cost `--test` provider remains useful as an installation smoke test, not as the main product experience.
- v0.1.0 was the paper/reproducibility-oriented release. v0.2.0 is the first release meant to make the repository look readable, presentable, and usable as software.
- The project is not stable or mature, and the docs should say so plainly without apologizing for it.

## Non-Goals For This Docs Branch

- Do not rewrite `README.md` yet. The README is user-owned for now; later work may do command/link consistency checks after the user's pass.
- Do not document the Clojure API, Python adapter, JSON bridge, or benchmark API here.
- Do not include a full language manual. Spell is mainly written by the language model; human docs should explain enough to understand traces, examples, and source structure.
- Do not advertise benchmark, paper, GCP, or notebook workflows as part of the public software surface.
- Do not add a separate `docs/traces.md` unless a later review shows the source guide cannot cover trace usage briefly.

## Work Package 2: Human-Facing Conceptual Documentation

Goal: create a short conceptual guide that a curious human can read before looking at examples or traces.

Tasks:

1. Add `docs/language-overview.md`.
   - Base it on the paper appendix, especially `notebook/writeup/paper/appendix/language_design_v3.md`.
   - Distill aggressively; target at most a few pages.
   - Write for a human reader trying to understand what Spell is doing, not for a user trying to hand-author large Spell programs.

2. Cover the core ideas only.
   - Self-programmed execution: the model writes the orchestration program.
   - Completions as executable programs.
   - `!llm-self` as the central self-call primitive.
   - Quines/self-reference.
   - The completion wrapper and prompt-as-prefix idea.
   - Double evaluation as the boundary that lets effectful trailing expressions run.
   - Context management at a high level: `!extend`, `!call-now`, `prune`, `persist`, `think`/`rethink`.
   - Agent communication at a high level: synchronous self-calls versus spawned agents.

3. Explicitly avoid over-documenting.
   - Do not reproduce the full appendix.
   - Do not turn this into a Clojure or Lisp tutorial.
   - Do not document removed or hidden features such as ReAct/explore as public features.
   - Do not include API examples.

4. Link from public docs.
   - Add links from public source guide and, after the user's README pass, optionally from README.

Deliverables:

- `docs/language-overview.md`
- Source-guide link to the language overview

Goal: keep useful orientation docs for readers and agents, while removing private/project-management context.

Status: completed in this docs branch.

1. Clean `AGENTS.public.md`.
   - Make it the canonical public source guide.

   - Keep source map, reading order, config map, and examples map.
   - Remove benchmark API, benchmark client, GCP, notebook, paper-management, and internal-branch references.
   - Remove ReAct/explore from the public feature map if those files are removed from the public surface.

2. Decide which `AGENTS.md` files are useful to public users.
   - Review `config/AGENTS.md`, `examples/AGENTS.md`, and `test/AGENTS.md`.
   - Keep them if they help a non-maintainer understand config, examples, or tests.
   - If kept, public-clean them and remove benchmark/notebook/private workflow references.
   - If they duplicate better docs, remove or replace them with ordinary docs.

3. Hide private/internal guidance.
   - Gitignore or remove from the public release surface:
     - `AGENTS.md`
     - `CLAUDE.md`
     - `config/CLAUDE.md`
     - `examples/CLAUDE.md`
     - `test/CLAUDE.md`
   - Preserve useful content elsewhere only if it belongs in public docs.

4. Public-clean config documentation.
   - Describe `config/agents/`, `config/providers/`, `config/prompts/`, `config/spl-lib/`, and `config/web.edn`.
   - Rename benchmark/runtime profile language to ordinary I/O profile language.
   - Document first-class public providers: OpenAI, Anthropic, Fireworks, and Codex CLI as an experimental/public path.
   - Do not make Ollama prominent unless later explicitly selected.
   - Document `SERPER_API_KEY` only as web/search configuration, not as benchmark setup.

5. Document trace tooling lightly.
   - Keep trace functionality in source guidance as a developer/debugging feature.
   - Mention `-T` and trace output briefly if useful.
   - Remove benchmark-result wording such as resolving latest errored benchmark records from public docs.

Deliverables:

- Cleaned `AGENTS.public.md`.
- Kept and public-cleaned `config/AGENTS.md`, `examples/AGENTS.md`, and `test/AGENTS.md`.
- Removed tracked private/internal guidance from the public release surface:
  - `AGENTS.md`

  - `test/CLAUDE.md`
